# ЭТАП 1. Пункт 1 и Пункт 2 (Анализ и DDD-проектирование)

Перед написанием кода любой проверяющий / преподаватель будет смотреть именно этот раздел (обычно в файле `README.md` репозитория).

## 📌 ПУНКТ 1: Выбор предметной области
* **Предметная область:** **Онлайн-магазин (E-Commerce Platform)**.
* **Обоснование выбора:** Данная доменная модель идеально ложится на микросервисную архитектуру, так как содержит независимые бизнес-процессы (каталог, заказ, складские остатки, списание средств, авторизация), требует асинхронной координации (Saga) и синхронной проверки доступности товара (gRPC).
* **Количество объектов (агрегатов):** **14 агрегатов** (удовлетворяет требованию «примерно 10–15 агрегатов»).

---

## 📌 ПУНКТ 2: Разделение по DDD (Bounded Contexts & Aggregates)

Вся система разделена на **3 основных ограниченных контекста (микросервиса)** + вспомогательный логистический поддомен:

```
+-----------------------------------------------------------------------------------+
|                                ОНЛАЙН-МАГАЗИН                                     |
+-----------------------------------------------------------------------------------+
        |                                   |                                |
        v                                   v                                v
+------------------+             +--------------------+            +-------------------+
|   AUTH CONTEXT   |             |   ORDER CONTEXT    |            | INVENTORY CONTEXT |
|  (auth-service)  |             |  (order-service)   |            |(inventory-service)|
+------------------+             +--------------------+            +-------------------+
| 1. User          |   gRPC      | 4. Order           |   Kafka    | 9.  Product       |
| 2. Credential    | <---------> | 5. OrderItem       | <--------> | 10. Stock         |
| 3. RefreshToken  |             | 6. OrderOutbox     |            | 11. Reservation   |
|                  |             | 7. SagaInstance    |            | 12. PaymentWallet |
|                  |             | 8. CustomerProfile |            | 13. PaymentInbox  |
+------------------+             +--------------------+            +-------------------+
```

---

### Контекст 1: Идентификация и безопасность (`auth-service`)
**Граница контекста:** Регистрация, аутентификация клиентов и администраторов, выдача и валидация JWT-токенов.

* **Агрегат 1: `User` (Пользователь)**
    * *Тип:* Root Entity (Корень агрегата).
    * *Поля / Value Objects:* `UserId` (UUID), `Email` (Value Object с валидацией формата), `FullName`, `UserStatus` (ACTIVE, SUSPENDED).
    * *Бизнес-инвариант:* Email уникален в системе; заблокированный пользователь не может выполнять операции.
* **Агрегат 2: `Credential` (Учетная запись)**
    * *Тип:* Root Entity.
    * *Поля:* `CredentialId`, `UserId`, `PasswordHash` (BCrypt), `Role` (Value Object: `ROLE_CUSTOMER`, `ROLE_ADMIN`).
    * *Бизнес-инвариант:* Пароль хранится только в виде необратимого хеша с солью.
* **Агрегат 3: `RefreshToken` (Сессия авторизации)**
    * *Тип:* Root Entity (хранится в Redis с TTL).
    * *Поля:* `TokenId`, `UserId`, `ExpiresAt`, `DeviceFingerprint`.
    * *Бизнес-инвариант:* При выходе из системы (Logout) или истечении времени токен немедленно инвалидируется.

---

### Контекст 2: Управление заказами (`order-service`)
**Граница контекста:** Прием заказов от клиентов, расчет итоговой стоимости, координация распределенной транзакции (оркестрация Саги).

* **Агрегат 4: `Order` (Заказ — главное ядро системы)**
    * *Тип:* Root Entity.
    * *Поля:* `OrderId`, `CustomerId`, `OrderStatus` (NEW, PENDING_PAYMENT, PAID, CANCELLED, COMPLETED), `Money` (TotalAmount — Value Object), `CreatedAt`.
    * *Бизнес-инвариант:* Заказ нельзя отменить, если он уже перешел в статус COMPLETED; сумма заказа не может быть отрицательной.
* **Агрегат 5: `OrderItem` (Позиция заказа)**
    * *Тип:* Entity внутри агрегата `Order`.
    * *Поля:* `OrderItemId`, `ProductId`, `Quantity` (целое положительное число), `UnitPrice` (зафиксированная цена на момент покупки).
    * *Бизнес-инвариант:* Количество единиц товара должно быть $> 0$; цена фиксируется на момент оформления и не меняется при изменении цен в каталоге.
* **Агрегат 6: `OrderOutbox` (Событие транзакционного Outbox)**
    * *Тип:* Root Entity (для реализации Outbox Pattern).
    * *Поля:* `EventId`, `AggregateType`, `AggregateId`, `EventType` (`OrderCreated`, `OrderCancelled`), `Payload` (JSON), `Status` (PENDING, SENT).
    * *Бизнес-инвариант:* Сохраняется в PostgreSQL строго в **одной транзакции** вместе с агрегатом `Order`.
* **Агрегат 7: `OrderSagaState` (Состояние распределенной саги)**
    * *Тип:* Root Entity.
    * *Поля:* `SagaId`, `OrderId`, `CurrentStep` (CHECK_STOCK, CHARGE_PAYMENT, CONFIRM_ORDER), `Status` (IN_PROGRESS, FAILED, SUCCEEDED).
    * *Бизнес-инвариант:* При получении отказа от склада или платежа сага обязана запустить компенсирующие действия.
* **Агрегат 8: `CustomerProfileSnapshot` (Снапшот данных покупателя)**
    * *Тип:* Value Object внутри заказа.
    * *Поля:* `DeliveryAddress`, `RecipientPhone`.

### Контекст 3: Склад, Каталог и Биллинг (`inventory-service`)
**Граница контекста:** Учет номенклатуры товаров, хранение складских остатков, бронирование товаров под заказ и списание средств со счета.

* **Агрегат 9: `Product` (Товар в каталоге)**
    * *Тип:* Root Entity.
    * *Поля:* `ProductId`, `Title`, `Description`, `Category`, `BasePrice` (Money).
    * *Кеш:* Кешируется в **Redis**, так как каталог просматривают значительно чаще, чем заказывают.
* **Агрегат 10: `InventoryStock` (Складской остаток)**
    * *Тип:* Root Entity.
    * *Поля:* `StockId`, `ProductId`, `TotalQuantity`, `ReservedQuantity`.
    * *Бизнес-инвариант:* Доступное количество (`TotalQuantity - ReservedQuantity`) не может стать меньше 0.
* **Агрегат 11: `StockReservation` (Бронь товара)**
    * *Тип:* Root Entity (участвует в Саге).
    * *Поля:* `ReservationId`, `OrderId`, `ProductId`, `ReservedAmount`, `Status` (ACTIVE, RELEASED, CONFIRMED).
    * *Бизнес-инвариант:* Если заказ отменен, зарезервированные товары должны вернуться в доступный остаток (компенсирующая транзакция).
* **Агрегат 12: `CustomerWallet` (Кошелек покупателя)**
    * *Тип:* Root Entity.
    * *Поля:* `WalletId`, `CustomerId`, `Balance` (Money).
    * *Бизнес-инвариант:* Списание невозможно, если `Balance < OrderAmount`.
* **Агрегат 13: `PaymentInbox` (Дедупликация входящих сообщений — Inbox Pattern)**
    * *Тип:* Root Entity.
    * *Поля:* `MessageId` (UUID события из Kafka), `ReceivedAt`, `Processed`.
    * *Бизнес-инвариант:* Одно и то же сообщение из брокера никогда не обрабатывается дважды (гарантия idempotency).
* **Агрегат 14: `PaymentTransaction` (История списаний и возвратов)**
    * *Тип:* Entity.
    * *Поля:* `TransactionId`, `OrderId`, `Amount`, `Type` (PAYMENT, REFUND), `Timestamp`.
